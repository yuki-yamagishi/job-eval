# 事前検証・パッチワーク点検記録 (Pre-Verification: Issue #76)

- **対象 Issue**: Issue #76: Pre-Phase 要件監査 (DoR) 導入と Fleet 完了性監査の反証型・過剰攻撃防止リファクタリング (ADR-0023)
- **実施日**: 2026-09-10
- **実施者**: Antigravity Agent

---

## 1. 現状確認・課題の再現

### 現状の問題点
- PR 段階の完了性監査（`fleet_completion_auditor`）は、親エージェントが作成した `issue.md` とコードを突き合わせるが、`issue.md` の受け入れ要件が抽象的・メタ的表現の場合、甘い基準を追認（Rubber Stamping）して合格を出してしまう。
- また、単に批判的レビューを求めると、完璧な実装に対しても言いがかりのような粗探しや過剰な攻撃的指摘（Nitpicking / False Positives）が発生して開発ループが停滞するリスクがあった。

---

## 2. 課題の分析・設計方針
- 監査のタイミングを「実装前」と「実装後」に分離（Shift-Left）。
- 反例提示義務とゴールポスト移動禁止により、過剰攻撃を物理防止。

---

## 3. 重複・パッチワーク点検 (Impact & Duplication Check)

### 3.1 既存サブエージェントおよびプラグイン構成
- `.agents/plugins/antigravity-review-loop/agents/`:
  - `fleet_reviewer.md`: コード品質・型安全性・セキュリティ専門（How の検証）。
  - `fleet_completion_auditor.md`: 完了性・Why 専門。現状は肯定的確認が中心で反例義務がなかった。
- **重複・パッチワーク点検結果**:
  - 新たに PR レビュアーを 3 人に増やすのではなく、Issue 作成時の Pre-Phase に `fleet_dor_auditor` を新設し、PR 作成後の Post-Phase は従来の 2 体体制を維持することで、無駄なトークン消費とプロンプト混濁を防止。

### 3.2 既存フック実装
- `.agents/plugins/antigravity-review-loop/hooks/`:
  - `branchDoRGate.js`: セクション存在チェックのみだったため、具体的な機能受け入れシナリオの記述検査および曖昧語検知を追加。テンプレート引用文の事前除去により False Positive を防止。
  - `prePrAuditGate.js`: 新フォーマット（5.2 Pre-PR DoD）および旧フォーマット（5.1 Pre-PR DoD）の双方を正確に抽出できるよう正規表現を刷新し、False Negative を防止。

### 3.3 ADR 整合性
- ADR-0019（Fleet 2者合議制）および ADR-0022（プラグイン化パッケージング）を継承・進化させ、ADR-0023 として 2段階監査と過剰攻撃防止ガードレールを体系化。過去の設計決定との矛盾は一切なし。

## 4. リスク・副作用の評価

1. **ブランチ作成遅延リスク**:
   - Pre-Phase で要件監査を挟むためブランチ作成に 1 サイクルを要するが、実装後の手戻り防止による工数削減効果が圧倒的に上回る。
2. **過剰攻撃リスクの封じ込め**:
   - 反例提示義務、ゴールポスト移動禁止、「ゼロ件恐怖症」排除の 4 原則により、言いがかりによるマージ遅延を物理防止。
