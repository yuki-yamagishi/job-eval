# Issue #47 4軸事前検証ログ (Pre-Phase Verification)

## 1. 4軸事前検証の観点

### ① 事前検証 / 技術的ボトルネック
- **PowerShell エスケープ問題**: Windows 環境下で `gh pr comment` に直接文字列引数を渡すと、ダブルクォーテーションや複数行改行、特殊記号、日本語がシェルで展開・破壊される恐れがある。これを完全に回避するため、`--body-file` オプションを利用し、UTF-8 エンコードの一時ファイル経由でコメントを渡す設計とする。また、処理終了時（エラー時含む）に確実に一時ファイルを削除する。
- **正規表現によるパース堅牢性**: レビュアーの出力フォーマットの微細なブレ（リスト記法 `- [must]`, `* [must]`, 見出し記法 `### [must]`, 太字記法 `**[must]**`, 英大文字小文字 `[MUST]`, `[good]` 等）に耐えうる正規表現パターンを採用する。

### ② UX / 開発者体験
- **称賛と指摘の明確な分離**: 従来の Conventional Comments 体系では称賛ラベルがなく、良い実装を `[nits]` で褒めた際に自己修復ループが「要対応指摘」と誤判定してループが終了不能になる危険があった。新設する `[good]` を指摘件数カウントから除外し、レビュアーが自由に褒められるようにすることで、開発者体験と自動ループの安定性を大幅に向上させる。
- **CLI & モジュール両対応**: 単体スクリプトとしてコマンドラインから手動実行できるだけでなく、プログラムからモジュールとして呼び出して `loopState.js` をシームレスに更新できるようにする。

### ③ データ永続性 / 互換性
- **状態管理マシンとの完全整合**: `scripts/harness/loopState.js` のスキーマ（`STATUS.NEEDS_FIX`, `STATUS.RESOLVED_LGTM`）と完全連携し、`[must]` や `[should]` の未解決件数に基づいて状態を決定論的に更新する。
- **ファイル安全クリーンアップ**: 一時ファイルは OS 標準の一時ディレクトリまたは作業ディレクトリ外に作成し、リポジトリを汚染しない。

### ④ テスト自律性
- **単体テスト網羅率 100%**: `tests/harness/parseReviewResult.test.ts` において、`[good]` の除外、`[must]`/`[should]` のブロック判定、`[imo]`/`[nits]`/`[ask]` の非ブロック判定、各種記法揺れ、異常入力を Vitest で完全にテストする。
- **モックによる安全な外部通信テスト**: `tests/harness/postPrComment.test.ts` では `gh` コマンド呼び出しをモック化し、テスト実行時に実際に GitHub API を叩かない安全なテストを構成する。
