# ADR-0023: 2段階監査（Pre-Phase DoR 要件監査 ＋ Post-Phase 反証型完了性監査）と過剰攻撃防止ガードレール

- **ステータス**: Accepted
- **決定日**: 2026-09-10
- **対象**: Customization Layer, Fleet Subagents, BranchDoRGate, Review Consortium

---

## 1. 背景と課題 (Context)

ADR-0019 および ADR-0022 により、2者 Fleet 並行合議制（コード品質担当 `fleet_reviewer` ＋ 批判的完了性担当 `fleet_completion_auditor`）がプラグイン配下へカプセル化され、自動自律レビュー基盤が整った。

しかし、実際の運用と分析を通じて、以下の構造的課題が特定された：

1. **GIGO（Garbage In, Garbage Out）と Issue 内輪の追認（Rubber Stamping）**:
   - PR 段階の完了性監査（`fleet_completion_auditor`）は、親エージェントが作成した `issue.md` と `walkthrough.md` を照合する。
   - もし `issue.md` の受け入れ要件が「〇〇を実装すること」「テストが存在すること」等の抽象的・メタ的表現に留まっていた場合、エージェントはその甘い基準を満たしたと報告し、監査者も「Issue のチェックボックスが埋まっているから合格」と追認してしまう。
   - その結果、Issue 本来の目的（Why）やユーザーが真に求める挙動との乖離が検知できず、PR 後に人間の手動レビューで毎回指摘が入る事態が生じていた。
2. **シフトレフト（Shift-Left）の欠落**:
   - ブランチ作成前の DoR Gate（`branchDoRGate.js`）はセクション見出しの有無を文字列照合するだけであり、要件定義の具体性や Given-When-Then シナリオの妥当性を監査する仕組みが存在しなかった。
   - 実装と PR が完了した後に目的乖離を指摘しても手戻りコストが大きすぎる。
3. **過剰攻撃・粗探し（Nitpicking / False Positives）のリスク**:
   - 単に「批判的になれ」「穴を探せ」とプロンプトで要求すると、完璧な実装に対しても言いがかりのような指摘や主観的嗜好の強要を乱発し、開発ループが停滞（Review Fatigue）するリスクがある。

## 2. 決定事項 (Decisions)

### 決定 1: 2段階監査体制（Two-Phase Auditor）の確立
監査のタイミングを「実装前」と「実装後」に明確に分離する：
- **Pre-Phase（Issue 作成時・ブランチ前）: `fleet_dor_auditor`（要件・DoR 専門）**:
  - 観点: Why の根本原因深掘り、受け入れ基準の具体性（Given-When-Then、境界値・異常系）、曖昧語（「適切に」「よしなに」「〇〇の改善」「など」）の排除、排除リスクの網羅性。
  - 合格判定: `READY_TO_BRANCH`
- **Post-Phase（PR 作成後）: `fleet_reviewer` ＋ `fleet_completion_auditor`（2者並行合議）**:
  - `fleet_reviewer`: コード品質・型安全性・セキュリティ・アーキテクチャ（How の検証）。
  - `fleet_completion_auditor`: Pre-Phase で合意された具体受入シナリオに対する反証的検証（What / Why の検証）。

### 決定 2: 過剰攻撃・粗探し防止ガードレール (Balance & Fairness)
「本質的な抜け漏れは絶対に防ぎつつ、良いものはスパッと合格（LGTM）にする」ため、以下の 4 ルールをサブエージェントプロンプトに組み込む：
1. **反例提示の義務化 (Counterexample Obligation)**:
   - 定性的な不安や推測でのブロッキング指摘（`[must]` / `[should]`）を禁止。
   - 指摘を出す場合は、必ず「前提 A のもとで入力 B が渡された際、システムが C のように破綻する」という客観的反例（Counterexample）の提示を義務付ける。反例が示せない場合は合格（LGTM / READY_TO_BRANCH）とする。
2. **ゴールポスト移動（後出し要求）の厳禁**:
   - PR 段階において、Pre-Phase で合意された受け入れ基準を満たしているならば合格とする。PR 段階で新しい要求を後出ししてブロックすることを禁止する（将来アイデアは非ブロッキングの `[imo]` に隔離）。
3. **「ゼロ件恐怖症」の排除と `[good]` による積極的評価**:
   - 明確な欠陥がない場合、無理に指摘をひねり出すことを禁止。優れた点には `[good]` を付与して即座に合格とすることをプロフェッショナルな監査と規定する。
4. **主観・スタイルの好みの `[must]` 化禁止**:
   - コードの書き方や命名の好みは `[nits]` または `[imo]` に留め、マージをブロックしない。

### 決定 3: `template_issue.md` の受入基準フレームワーク刷新
- メタ的なプロセスチェックリストと機能受け入れ基準を分離：
  - `5.1 機能受け入れシナリオ (Given-When-Then & 境界値・異常系)`
  - `5.2 PR作成前プロセス完了基準 (Pre-PR Process DoD)`
  - `5.3 マージ前完了ゲート (Pre-Merge Gate)`
- 曖昧語の使用を禁止規約として明記。

### 決定 4: `branchDoRGate.js` の機能受入シナリオ検証強化
- 単に見出しが存在するだけでなく、`issue.md` の受け入れ基準セクションに具体的なシナリオや検証条件（`シナリオ` / `Given` / `When` / `Then` / チェックリスト）が記述されていることを物理検証する。

## 3. 影響と評価 (Consequences)

### ポジティブな影響
- **Why・要件乖離の根絶（シフトレフト）**: 実装前に要件が具体化されるため、手戻りや「作ってみたら違った」という根本的欠陥が激減する。
- **追認（Rubber Stamping）の防止**: Given-When-Then シナリオが明確に定義されることで、PR 監査アーが客観的かつ実質的な検証を行えるようになる。
- **開発リズムの維持**: 反例提示義務とゴールポスト移動禁止により、不当な難癖や粗探しによるレビューの長期化・ブロッカー乱発を防止できる。

### トレードオフ・受容コスト
- **ブランチ作成前の対話・監査ステップの追加**: Issue 作成後に `fleet_dor_auditor` による DoR 監査を挟むため、ブランチ作成までの準備に 1 サイクルを要する。しかし、実装・PR 後の手戻り・書き直しコストに比べれば微小であり、全体の開発速度と品質は大幅に向上する。
