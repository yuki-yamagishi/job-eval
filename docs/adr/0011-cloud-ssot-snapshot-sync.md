# ADR-0011: クラウド SSoT（唯一の正本）の確立とマージ機能全廃によるスナップショット同期の採用

- **ステータス**: Accepted
- **決定日**: 2026-09-04
- **決定者**: JobEval 開発チーム
- **関連Issue**: [Issue #32](https://github.com/yuki-yamagishi/job-eval/issues/32)

---

## 1. 背景と課題 (Context & Problem Statement)

これまでの開発において、既存実装をなるべく変更しない方針（差分最小化）で機能を追加してきた結果、以下の重大な構造的矛盾が発生していた：

1. **分散マージ（`smartMerge`）によるデータの競合・汚染**:
   - 単一ユーザーによる端末間同期（PC ↔ スマホ）であるにもかかわらず、複数人同時編集のような配列マージ・Last-Write-Wins（LWW）比較を行っていた。
   - 初期プロファイル（`DEFAULT_USER_PROFILE`）の `updatedAt` がアクセス時の現在時刻（最新）となっていたため、新端末やデプロイ直後に開いたサンプルデータがクラウド上のユーザー本番データを上書き破壊する事象が発生。
2. **削除求人のゾンビ復活**:
   - Cloudflare D1 同期 API が追加・更新（Upsert）のみを行っており、端末側で求人を削除しても D1 からは行が消えず、別端末や新端末で開いた際に削除したはずの求人が再出現していた。
3. **通信経路の二重化と不安定性**:
   - WebSocket（ntfy.sh）で求人・プロファイルの全データを直接送受信しようとしており、パケットサイズ肥大化による通信エラーや状態の不整合が発生していた。

---

## 2. 検討された選択肢 (Considered Options)

### 選択肢 1: スマートマージの延命・パッチ追加（Tombstone / 削除フラグの導入）
- **メリット**: 既存のマージコード（`smartMerge.ts`）を再利用できる。
- **デメリット**:
  - 論理削除フラグ（Tombstone）や複雑なベクター時計の管理が必要になり、個人用アプリに対してコードベースが過剰に複雑化する。
  - 継ぎ足しによる不具合の再発リスクが極めて高い。

### 選択肢 2: マージ全廃と Cloudflare D1 を SSoT（唯一の正本）とする完全スナップショット同期への刷新
- **メリット**:
  - **正本の明確化**: クラウド（D1）が唯一の正本（SSoT）となり、同期接続時はクラウドデータをそのままローカルに展開（上書き）するため、初期値による上書き事故が 100% 根絶される。
  - **削除の完全同期**: PUSH された求人リストを完全スナップショットとして D1 に反映し、リストに含まれない旧求人を D1 から物理削除することで、ゾンビ復活を根絶。
  - **コードの劇的な簡素化**: 複雑怪奇な `smartMerge.ts` を全廃可能。
  - **通信の安定化**: WebSocket は更新通知シグナル（Ping）のみとし、データ実体は D1 から Pull する構成に統一。
- **デメリット**: 同一アカウントで2端末が同時に別々のオフライン編集を行った場合、後から保存した端末のスナップショットで上書きされる（ただし単一ユーザー利用のため実用上問題なし）。

---

## 3. 決定内容と理由 (Decision Outcome & Rationale)

### 採用: **選択肢 2（クラウド SSoT ＋ スナップショット同期 ＋ マージ全廃）**

### 決定理由:
1. **ユーザー体験の直感性**:
   - 単一ユーザーの端末間引き継ぎにおいて、求められるのは「最後に保存した端末の状態がそのままクラウドに残り、他端末はそれをそのまま開く」という極めてシンプルな挙動である。
2. **保守性と堅牢性**:
   - 対症療法のパッチを重ねるのではなく、不要な分散マージロジックを完全に排除することで、データロストやゴーストデータの発生要因を根絶する。
3. **安全な初期展開**:
   - `DEFAULT_USER_PROFILE.updatedAt` を `1970-01-01T00:00:00.000Z`（最古）に固定し、同期ルーム接続時はクラウドのデータでローカルのサンプルデータを無条件で破棄・置換する。

---

## 4. トレードオフと影響 (Consequences & Trade-offs)

### メリット (Positive Impact)
- デプロイや新URLアクセス時にプロファイルが初期値に戻る問題が根絶される。
- 求人削除がクラウド（D1）および全端末で確実に反映され、ゾンビ復活が解消される。
- `smartMerge.ts` の廃止により、テストおよびコードベースの保守性が大幅に向上する。

### デメリット・制約 (Negative Impact / Limitations)
- 複数人による同時タイピング（Google Docs 的なリアルタイム共同編集）はサポートしない（設計思想上、意図された制約）。
